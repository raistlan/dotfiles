# Work with a Linear project

1. Open the Linear project the user named or linked. Ask for its resources; a fetch that omits them returns no documents and looks the same as a project that has none.
2. Locate the project's governing documents. Look for a `Ways of working`, working agreement, or agent contract, and for a tech spec, glossary, decision log, and behavioral contracts.
3. Read the working agreement first. Follow where it points; a good one names the rest of the governing set.
4. Read every governing document that bears on the task, not the working agreement alone.
5. Check the status of each decision that affects the task. A decision log separates current decisions from outdated, contradicted, and overridden ones. Neither document order nor recency settles a conflict.
6. Read the whole issue, plus its parent, its sub-issues, and its blocking relationships.
7. Follow the working agreement for the rest of the task.
8. Treat the Linear project as authoritative over local copies, chat memory, and inferred conventions.

Report any conflict between two governing sources, or between a source and an issue, and stop the affected work. Do not resolve it yourself.

If the project has no governing documents, stop and ask the user for them or for access. Do not invent a project workflow. If the project has some governance but no working agreement, work from what is there and say what is missing.
